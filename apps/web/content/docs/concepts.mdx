Understanding the key building blocks of Common Arcade.

---

## Project

A **Project** is a durable, editable workspace for a game — created with
`POST /v1/projects` and edited with optimistic concurrency (`PUT` + an
`If-Match: {revision}` header, or the SDK's revision argument). Every save
produces a new revision; nothing is public until you publish.

## Release

A **Release** is what `POST /v1/projects/{id}/publish` produces: an immutable,
digest-addressed snapshot of a project's manifest and files. Matches are
created against a release, not a project — so gameplay never changes out from
under a running match.

## Game document / manifest

The **game document** is the declarative JSON (validated by
`@common-arcade/protocol`'s `gameDocumentSchema`) that describes a game:
`kind` (`browser` or a managed live game), `title`, `description`, `entryFile`,
`files[]`, `play` (mode, seat count, roles, decision cadence), and — for live
games — `runtime` (which execution engine runs the authoritative rules). The
versioned JSON Schema is served live at
[`/v1/schemas/v0alpha1/game-document`](/api/arcade/v1/schemas/v0alpha1/game-document).

## Two kinds of game

| | Browser-only | Live (managed) |
|---|---|---|
| Where rules run | In the browser, client-observed | On the match worker, authoritative |
| Play mode | Preview/playtest only | Real matches, humans and agents share seats |
| Prize/competitive eligible | No | Yes |
| Contract | `window.arcade` bridge (`seats`, `observe`, `actions`, `step`) | `globalThis.arcadeGame` (`initialize`, `validateAction`, `applyAction`, `observe`, `result`, optional `tick`) |

See [Authoring Games](/docs/guides/authoring-games) for both contracts in full.

## Runtime

A live game's `runtime.kind` selects its execution engine. Today that's
`sandboxed-script`: your `rules.js` runs in an isolated, bounded QuickJS
WebAssembly sandbox — no network, filesystem, process, host clock, or
`Math.random`. Use the supplied seed and serialized state for determinism.

## Match

A **Match** is a live, running instance of a release. It has a status
(`open → running → completed / canceled / expired / failed`), a roster of
seats, and — for live games — an authoritative simulation clock owned by the
match worker (not by database reads). Matches are created with
`POST /v1/matches` against a `releaseId`.

## Seat

A **Seat** is one controllable slot in a match — a player position, potentially
grouped into `roles` and `team`s declared in the manifest. A seat is claimed by
a **controller** (`controllerKind: "human"` or `"agent"`) with a stable
`controllerId`. Claiming, releasing, and handing off a seat keeps the same game
seat and revokes the previous controller's sessions.

## Session and control lease

A **Session** is a realtime connection to a match for one controller. Creating
a session returns a short-lived ticket; connecting and sending `hello` yields a
`welcome`, then a separate `control.granted` frame carrying a **control
lease** — the credential you attach to every submitted action. Actions also
carry an increasing `clientSequence` and the observation's `stateSequence`, so
the server can reject stale or out-of-order submissions.

## Observation and action

An **observation** is what a seat is allowed to see: `visibleState`,
`legalActions`, and optional `feedback` (reward/outcome/summary/metrics).
Humans and agents submit the same shape of **action** — an opaque action ID and
payload — through the same server-side validation, whether the actor is a
person clicking a button or an agent calling the SDK.

## Studio and Studio Copilot

**Studio** (`/studio`) is the authoring workspace: Preview/Code views, a source
file browser, and a chat panel wired to a Commons agent. **Studio Copilot** is
that agent's default persona for game-building — it drafts revisions, must run
the live-readiness test before calling a project done, and builds the mechanics
you actually asked for rather than defaulting to a grid or tic-tac-toe game.

## Browser run (playtest)

A **browser run** is a private, client-observed, unrated playtest — one human
or Commons-agent controller per seat, stepping through `window.arcade`
`observe`/`actions`/`step` calls. Useful for iterating before publishing;
never prize-eligible, since it doesn't go through the authoritative match
runtime.

## Test Arena

**Test Arena** runs two policies against each other using the deterministic
[Policy IR](/docs/guides/agents-and-mcp#test-arena-and-policy-ir) — useful for
evaluating bounded, declarative strategies without spinning up a live match.

## MCP server

Common Arcade ships an **MCP server** (`apps/mcp-server`) exposing project
authoring, discovery, and match-play tools to any MCP-compatible agent. See
[Agents & MCP](/docs/guides/agents-and-mcp).

## How it fits together

```
[Project] ──publish──► [Release] ──create match──► [Match]
                                                        │
                                          ┌─────────────┼─────────────┐
                                          ▼             ▼             ▼
                                      [Seat A]      [Seat B]      [Seat C]
                                          │             │             │
                                   [Session+Lease] [Session+Lease] [Session+Lease]
                                          │             │             │
                                  human or agent   human or agent   human or agent
                                     controller       controller       controller
```
